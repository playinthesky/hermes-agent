# 캠프 운영·출시 플레이북 — 숙의공론 컨설팅 플랫폼

> 작성: 빙허각 / 운영 허브: 파발(擺撥)
> 목적: 6인 캠프를 **빠른 출시 엔진**으로 바꾼다. 대표님이 짚은 4가지 통증
> (① 클로드 코딩 불안 ② 코덱스 이해력 ③ 코덱스 비용 ④ 소통 단절)을 한 번에 푼다.
> 단일 진실은 `kspeaks-agora/AGENTS.md`. 이 문서는 그 위의 **실행 운영서**다.

---

## 1. 진단 한 줄 요약

문제는 도구가 아니라 **일을 던지는 방식**이다.
- 클로드는 **명세·리뷰**에 강하고 **큰 덩어리 구현**에 약하다 → 강점에만 쓴다.
- 코덱스는 **모호한 큰 요청**에 약하다 → 작은 명세를 주면 잘 따라온다.
- 코덱스 비용은 **두뇌(모델)를 OpenAI에 고정**해서 난다 → 두뇌만 갈아끼운다.
- 소통 단절은 **사람이 메신저**라서 난다 → 파발이 24시간 허브로 메운다.

---

## 2. 6인 → 린(lean) 루프 재편

출시 전까지는 **상시 3역 루프**로 좁힌다. 나머지는 필요할 때만 호출.

| 역할 | 누구 | 하는 일 |
|---|---|---|
| **설계자** | 빙허각 (+필요 시 본승지) | 작업을 작은 단위로 쪼개 **명세**(받아들임 기준+테스트)를 쓴다. 코드 **리뷰**. |
| **허브·전령** | 파발 (Hermes, 슬랙) | 대표님 의도를 명세로 정리, 인박스로 위임, 결과 회수·보고, PR 자동 리뷰. 24시간. |
| **실행자** | 별동수 1명 (싼 두뇌로) | 명세 1개를 정확히 구현해 **draft PR**. |

- 소춘풍·모별감은 **즉답·외부 확인용** 보조. 구편수는 **구글 연동·자동화**가 필요할 때만.
- 원칙: **동시에 떠 있는 실행자는 1명.** 실행자가 둘이면 충돌·중복으로 속도가 죽는다.
- "위원회 6명"이 아니라 "한 줄 파이프라인 + 대기 인력"으로 본다.

## 3. 명세 → PR → 리뷰 루프 (핵심 표준)

모든 작업은 이 루프를 돈다. **작게 쪼갤수록** 이해력·신뢰도·소통이 동시에 좋아진다.

```
대표님/빙허각  ──①명세──▶  GitHub Issue(codex 라벨)  ──②구현──▶  draft PR
      ▲                                                              │
      └──────────④머지/반려──  파발·빙허각 ◀──③diff 리뷰───────────┘
```

### ① 명세 1장 규격 (이게 80%를 좌우한다)
하나의 Issue = 하나의 작업. 본문에 반드시:
- **목표**: 한 문장. "무엇을 왜".
- **입력/출력**: 어떤 데이터·화면이 들어오고 나가나.
- **받아들임 기준**: 체크박스로. "X 하면 Y 된다" 식의 검증 가능한 문장.
- **테스트**: 통과를 어떻게 확인하나(명령·시나리오).
- **건드리지 말 것**: 보호 자산(`app.py`·`templates/`·`db/` 등) 명시.
- **크기 가드**: 변경 파일 ≤ 3개, 한 번에 반나절 분량을 넘기면 더 쪼갠다.

### ② 구현 규칙 (실행자)
- 명세 범위 밖은 손대지 않는다. 애매하면 **추측 말고 Issue에 질문**.
- `main` 직접 금지 → 항상 draft PR. 커밋 메시지 명확히. 끝에 서명.

### ③ 리뷰 (파발/빙허각)
- diff만 본다. 받아들임 기준 체크박스를 하나씩 대조.
- 반려는 **구체적 한 가지**씩. "전반적으로 별로"는 금지.

### ④ 머지
- Doc-only(`docs/`·`training/`·`AGENTS.md` 등) + CI 통과 + 미해결 리뷰 0 → 파발이 자동 머지.
- 코드·인프라·운영 자산 → **대표님 명시 신호** 후 머지.

## 4. 코덱스 두뇌 교체 — 비용 즉시 절감 (작은 명세 1호)

**핵심 사실**: `byeoldongsu_runtime/openai_agent.py` 가 OpenAI에 고정돼 있어 비용이 난다.
`base_url` 한 줄만 열면 같은 별동수가 **OpenRouter / Nous Portal의 싼 코딩 모델**로 돈다.
이게 이 플레이북의 첫 실전 명세다(아래를 그대로 Issue로 박으면 된다).

> **[별동수] 별동수 런타임 두뇌를 OpenAI-호환 엔드포인트로 전환**
> - 목표: 별동수가 OpenAI 외 OpenAI-호환 제공자(OpenRouter/Nous)도 쓰게 한다. 비용 절감.
> - 변경:
>   1. `byeoldongsu_runtime/config.py` 에 `openai_base_url()` 추가 — `os.environ.get("OPENAI_BASE_URL")` 반환.
>   2. `byeoldongsu_runtime/openai_agent.py` 의 클라이언트 생성을
>      `OpenAI(api_key=api_key, base_url=config.openai_base_url() or None)` 로 변경.
> - 받아들임 기준:
>   - [ ] `OPENAI_BASE_URL` 미설정 시 기존(OpenAI)과 동일하게 동작.
>   - [ ] `OPENAI_BASE_URL=https://openrouter.ai/api/v1` + 해당 키 + `OPENAI_MODEL=<코딩 모델>` 설정 시,
>         `codex` 라벨 테스트 이슈에 그 모델로 응답한다.
> - 테스트: `python -m unittest tests.test_byeoldongsu_runtime -v` 통과 + 테스트 이슈 1건 실제 응답.
> - 건드리지 말 것: `app.py`·`templates/`·`static/`·`db/`. (런타임 폴더만 수정)
> — 빙허각

**운영 환경변수**(Railway, 코드에 박지 말 것):
- `OPENAI_BASE_URL` = OpenAI-호환 제공자 주소 (예: OpenRouter `https://openrouter.ai/api/v1`)
- `OPENAI_API_KEY` = 그 제공자 키
- `OPENAI_MODEL` = 싸고 코딩 잘하는 모델 슬러그

**모델 고르는 법(정직하게)**: "어느 게 최고"를 외우지 말고, **받아들임 기준 통과 + 가장 싼 것**을
고른다. 후보를 2~3개 띄워 같은 명세로 돌려보고(③ 리뷰로 채점), 통과율 대비 단가가 좋은 걸 남긴다.
강한 코딩 작업 한두 개는 파발이 직접 Claude(자기 API 키)로 처리하는 혼용도 가능 —
**Hermes는 작업별로 모델을 바꿀 수 있다**(`hermes model`). 비싼 코덱스 구독에 묶일 이유가 없다.

## 5. 플랫폼 MVP 범위 — "한 줄기 끝까지"

빨리 완성하려면 기능을 **넓게 깔지 말고**, **하나의 워크플로를 끝까지** 동작시키는
세로 슬라이스(vertical slice)부터 박는다. 이미 캠프에 단서가 있다:
- `kspeaks-agora/docs/WORKFLOW_공론장.md` — 발주→프로젝트→플로어플랜→패킹→파워→현장 흐름
- `kspeaks-agora/orchestrator/spec/v0.1.md` — 오케스트레이터 명세 골격

### MVP 정의 원칙
1. **하나의 고객 시나리오**를 처음부터 끝까지 굴린다 (등록→숙의→분석→리포트 등 한 줄기).
2. 그 줄기에 **꼭 필요한 화면·API만**. 나머지는 백로그.
3. 데모 가능한 상태(대표님이 클릭으로 시연)를 매주 1번 갱신.

### 범위를 박으려면 대표님 입력이 필요합니다 (제가 추정으로 못 만드는 부분)
- 🎯 **첫 고객/시연 대상**은 누구이고, 언제까지 보여줘야 하나요?
- 🧩 숙의공론 플랫폼이 **꼭 해야 하는 한 가지 워크플로**는 무엇인가요?
  (예: "온라인 설문 → STM 분석 → 숙의 리포트 자동 생성")
- 🔗 기존 `kspeaks-agora`(아고라 앱)를 **확장**하나요, **새 서비스**로 분리하나요?
- 📦 데이터는 지금처럼 Google Sheets 유지인가요, 별도 DB로 가나요?

→ 위 4개만 답해 주시면, 제가 그 줄기를 **명세 5~8장**으로 쪼개 인박스에 박고
파발이 별동수에게 순서대로 위임하도록 셋업하겠습니다. 그게 "출시까지의 백로그" 1번이 됩니다.
